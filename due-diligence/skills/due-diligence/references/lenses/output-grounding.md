# output-grounding — Is model output validated before anything downstream trusts it?
> Cites: res_llm-safety.md

## Fires on
Tags: llm-pipeline. Any artifact where an LLM's output feeds a downstream action, sink, or consumer — a shell/SQL/HTML sink, a file, an API call, a report, or another model call.

## Attacks
- Model output used without validation: text/JSON/code from the model reaches a downstream sink or action with no schema, type, or sanity check (OWASP LLM05, Improper Output Handling).
- Hallucination surface: an unverified fact, number, or claim generated by the model is passed downstream as if confirmed, with no cross-check against a ground-truth source.
- No fallback on bad output: malformed, empty, or out-of-range model output has no defined fallback path — it either crashes, silently passes through, or corrupts the next step.
- No schema/type check: structured output (JSON, function-call args) is consumed without validating shape/types before use, letting a malformed field propagate.

## Evidence of attack (clean-pass proof)
Name the specific validation step between model output and its consumer: the schema/type check, the sink-specific encoding (SQL param, HTML escape, path allow-list), or the cross-check against a ground-truth source for factual claims. Show what happens on validation failure — the fallback path, retry, or reject — and confirm it's deterministic, not model self-restraint. "Output looks fine" without naming the validation step and the failure path is not evidence.

## Severity guide
- blocker: unvalidated model output drives a consequential action (write, send, spend, delete, render unescaped) with no check.
- should-fix: a check exists but there's no defined fallback for a validation failure, or a fact is passed downstream unverified but low-stakes.
- nit: missing logging/monitoring on output validation failures, otherwise a working check.
