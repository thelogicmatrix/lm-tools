# projects: the portfolio layer

`docs/projects/` is where you read what every project is and where it stood, weeks
later. Two jobs, both page-level: cold-resume memory across more projects than fit in one
head, and steering via each page's Future Directions. It is deliberately *not* a
what-should-I-do-today dashboard.

The CLI owns every mechanic. `INDEX.md` is rendered from `docs/projects/_projects.json`
on every mutating verb, so a hand-edit to the table is overwritten and lost. Never edit
either file. A write-guard hook exists to deny `Write` and `Edit` on both and point the
caller back at the CLI.

`projects` below is `node "${CLAUDE_PLUGIN_ROOT}/skills/projects/projects.mjs"`. It stores
under `docs/projects/` in the current git repo, or under `$PROJECTS_ROOT` when that is set.

| Trigger | Do this |
|---|---|
| "projects" / "project status" / "portfolio" | Run `projects` with no arguments, relay its output verbatim. **Stop.** |
| status prose changed for a project | Write the body, pipe it: `echo "<body>" \| projects current <slug>`. **Stop.** |
| a project started, paused, went background or finished | `projects status <slug> active\|paused\|ops\|done`. **Stop.** |
| a new project needs a row | `projects register <slug> --name "<N>" --status <s> --where "<W>" --repo <R>`, then write its narrative into the page by hand. |
| "projects sync" | Run `projects sync`, then act on the flags. The user arbitrates concept-level truth, never rewrite a narrative to match reality without asking. |
| a project is done | Confirm with the user, then `projects archive <slug>`. |
| a project moved worktree, or got a repo, or its name changed | `projects set <slug> --where "<W>" --repo <R> --name "<N>"`. Pass only what changed. `--repo ""` clears it when a checkout is gone. |
| a slug is wrong, ugly or disagrees with gtg's | `projects rename <old> <new>`. It moves the page with the slug. Never rename by hand, the store is guarded. |
| "what happened to X" / "when did I last touch X" | `projects log [slug]`, relay it. **Stop.** |
| `INDEX.md` disagrees with the store | `projects render`. Never fix the table by hand. |
| a critique or a stray idea needs a home | Add it to `CRITIQUES.md` or to the project page's Future Directions. **Stop.** |

**Zero-model rule:** shell out, relay the output, do not reason about the JSON and do not
re-derive any number the CLI printed. Every mutation takes the **slug**, never a list
number, because list numbers re-sort. Each mutating verb commits its own files.

Each list row carries the slug in square brackets, which is where the slug for a mutation
comes from. Never read `_projects.json` to find one, and never take it from a page
filename, which diverges from the slug the moment either is renamed:

```
1. Demo Project [demo] (active): Registered 2026-08-04. No status written yet.
```

`projects status <slug> done` leaves the row in place. `projects archive <slug>` is what
moves the page into `archive/` and drops the row.

If a verb refuses with `Migrate it first`, `INDEX.md` still holds a hand-typed table that
was never migrated into `_projects.json`. Every verb is refused on purpose, because any of
them would render an empty index over the table. Stop and tell the user. Do not hand-write
the store and do not touch the table.

## What the model still owns

The narrative and Future Directions on each page, and the *body text* passed to `current`.
Everything else is the CLI's. A page's `## Current state` block is replaced wholesale on
every `current`, which is why status can never accumulate into a log again.

## Page shape

`register` writes this skeleton for a new project, and adopts an existing page rather than
overwriting it. The `*last verified ...*` stamp and the `## Current state` heading must
each start at the beginning of their line:

```markdown
# <Name>
*last verified never · docs: none*

<!-- projects:narrative-unwritten -->

## Current state (YYYY-MM-DD)
<!-- projects:current-state:start -->
Registered YYYY-MM-DD. No status written yet.
<!-- projects:current-state:end -->

## Future Directions

## Docs map
```

Replace the `narrative-unwritten` marker with the narrative. `sync` flags the page while
that marker is still there.

The header does not carry the status. `status` writes the store and never the page, so a
status on the page would be the registration status forever. The list row and `INDEX.md`
are where the status is read.

`current` reads the body from stdin and replaces everything between the start and end
markers, absorbing the `## Current state` heading above them. A page with no markers at
all gets the block inserted above `## Future Directions` when that heading is preceded by
a newline, and appended at the end of the page otherwise, which includes a page whose very
first line is that heading. On a page whose markers it cannot bound it throws and writes
nothing, deliberately, rather than guessing where the block ends and cutting into the
narrative. A page in that state is fixed by hand.

The `last verified` stamp is read from the page header only, meaning the text above the
first `## ` heading and above the start marker, and only from the **first** line-initial
`*last verified ...*` line in it. An indented stamp is not read at all, so a page carrying
a real date four spaces in reports as unverified, and a date in prose below the stamp is
not read either. `register` writes `last verified never` and no verb ever writes a real
date there, so the stamp moves only when a human has actually re-read the narrative.

## Reading a sync report

`sync` reports and never rewrites. Every flag line is `TOKEN <slug or page>: <why>`, one
line each:

- `NARRATIVE-UNWRITTEN`, the page is still the skeleton.
- `UNVERIFIED`, the header carries no usable `last verified` date, or the status has moved
  on past it.
- `NO-PAGE`, the row has no page, or points at one that is not on disk. `NO-ROW`, a page
  has no row.
- `NO-CURRENT-STATE`, the page has no dated Current state heading.
- `DOUBLE-HEADING`, the page carries more than one Current state heading.
- `STALE`, the status is behind the repo's last commit.
- `MISSING-REPO`, the row's repo path is not on disk.
- `MALFORMED`, `sync` has no block it can use on that page and refuses to guess. This one
  exits 1. Open the page and fix it by hand.

## Renaming a slug

`projects rename <old> <new>` is the only sanctioned way. It moves the page with the slug so
the two stay in step, and it refuses rather than guessing in the three cases that would lose
something: an unknown source, a target already registered, and a target whose page file
already exists on disk under another row's narrative.

Two things it deliberately does not do. It never bumps `Last touched`, because a rename is
bookkeeping and not work, and bumping it would restart the staleness window `sync` measures.
And it leaves a page whose basename had already diverged from its slug exactly where it is,
on the grounds that a page named differently was named that way on purpose.

**gtg keeps its own slug for the same project, and the two can disagree.** Renaming here does
not rename there. Run `gtg rename <old> <new>` as well when the point is to make them match.

One reference points the other way: a gtg entry names the family it belongs to by a
**portfolio** slug, in its own `parent` field. So a rename here can dangle a reference in a store
this CLI does not own, and the cost is quiet, because an unresolved parent merely lists that
project as standalone. `rename` therefore reads gtg's two stores, never writes them, and prints
a `NOTE:` naming every entry still pointing at the old slug together with the `gtg rename`
command that re-points them. Relay that note. It is the one part of a rename left undone.

## What happened, and when

`projects log [slug]` reads git rather than any ledger, because every mutating verb already
commits with a descriptive subject. So the history reaches back past this CLI into the
hand-edited era, and there is no second record to keep in step. Bare, it reports the store
and the index. Given a slug it follows that project's page, which is the one view the store's
own history cannot produce, since a renamed page looks like a delete plus an add without it.

## What `repo` buys, and when to leave it blank

`repo` is what lets `sync` check a project against reality rather than against itself. `STALE`
compares the project's stated state to that repo's last commit, and `MISSING-REPO` fires when
the path is gone. A row with no `repo` is invisible to both.

So set it on every project that has its own checkout, with `projects set <slug> --repo <path>`.
Leave it blank on a docs-only, Notion-only or home-checkout project, and that is not a gap:
pointing such a row at the home repo would compare it against a repo that commits many times a
day for unrelated reasons, so `STALE` could never fire and the check would be noise wearing the
costume of a signal.

## Seams

- **gtg**: a wrap distils its handoff into `projects current <slug>` and sets status via
  `projects status`. The handoff is the long form and already durable, so the page never
  restates it. Resume flips status back to `active`.
- **living-docs**: a project with its own `docs/` keeps its session entries there.
  `projects` never writes into another project's `docs/`.
- **CRITIQUES.md**: still a drop point for ad-hoc critiques. The routing procedure was
  removed 2026-07-29 after 25 days with zero entries. Restore it if the file starts
  getting used.
